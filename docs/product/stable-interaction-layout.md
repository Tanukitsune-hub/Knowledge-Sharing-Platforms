# 操作位置を安定させるレイアウト・状態表示の方針

更新日: 2026-09-25
方針: 採用 / 実装は後続Work
実装Work ID: 0071
Canonical product direction: YES

## 目的と根拠

利用者から、ファイル選択や保存操作の後に保存用ファイル名・「保存しています」等の表示が追加され、段数が増えてボタンが下へ動くとの指摘があった。これを装飾の問題ではなく、操作位置と読み進めている位置の予測可能性の問題として扱う。

本書は、この会話で合意した今後の製品方針を記録する。今回の記録作業では画面の移動量を実測しておらず、実装済み・検証済みとは扱わない。

目標は「処理状態が変わっても、押す場所を探し直さなくてよい」ことである。処理状態の通知を隠したり、重要なエラーを省略したりして見かけ上の安定を作らない。

## 現在のWorkとの境界

- Work0070 / 0070-CODEX-03の実装範囲、固定済みcandidate、Acceptance Evidence、権限、実行上限を変更しない。
- 本方針をWork0070の追加Acceptanceや完了阻害要因にしない。現在のWorkを先にレビュー・収束させる。
- UI改善の実装Workは0071として予約済み。本書の追加だけではCodex Dispatchを開始せず、Work0070完了後に別Dispatchを発番する。
- 保存・採番・retry・競合制御・権限・schema・provider・全文出力の内容範囲は本方針だけでは変更しない。

## 共通原則

1. 操作エリアを、伸び縮みする本文・ファイル一覧・結果表示から分離する。保存、検索、集計などの主要ボタンを、非同期通知やファイル名の追加で押し出さない。
2. 通常の処理中・完了表示は、あらかじめ用意した状態表示枠の内容更新で伝える。通知のたびに上部へ新しい段を挿入しない。
3. 通常・処理中・完了の切り替えで主要ボタンの位置・寸法を安定させる。ボタンの追加・削除やラベルの折り返しで、別の操作が直前のクリック位置へ移動しない。
4. 利用者が明示的に詳細を開く等、必要な内容の展開は認める。すべての高さ変化を禁止するのではなく、意図しない操作対象・閲覧位置の移動を抑える。
5. 通知のためにフォーカスを奪ったり、勝手にスクロールしたりしない。入力エラーへの適切なフォーカス移動等は、対象と理由が明確な例外とする。
6. 見た目の遮蔽だけに頼らず、処理中の二重送信や不正な変更は既存の制御で防ぐ。無関係な画面や別利用者まで待たせない。

## レイアウトの第一案

### 主要操作エリア

- 各画面・各編集領域の上部に主要操作をまとめる案を第一候補とする。すべての行操作や補助操作まで上部へ集めない。
- 長い入力画面では、その領域内での追従表示を検討する。画面幅、拡大表示、ソフトウェアキーボード、フォーカス対象を覆わないことを優先し、全面固定を一律に適用しない。
- 保存とクリアは視覚的な優先度・配置で区別する。処理後に保存ボタンを消し、その位置へクリア等を移動させない。
- ボタンをDOM上で移す場合も、フォームとの関連、Enter送信、キーボード順序、対象record、既存handlerの単一性を維持する。見た目の改善のために別の保存経路を作らない。

### 状態通知

- 短い通常通知は、コンパクトな予約済み領域で置き換える。大量の常時空白を確保する方式にはしない。
- 詳細は明示的に開ける領域へ分ける。ただし失敗理由や次の対応が分からなくなる切り詰めは禁止する。
- 成功、部分成功、失敗、保存結果不明、競合を区別する。例: 面談メモが保存済みでも資料が未完了なら、両方を正確に表示する。
- 要対応の失敗・部分成功・保存結果不明は、一瞬で消える通知だけにしない。対象record/fileと再試行・確認方法を残す。
- 状態変更は読み上げにも伝える。過剰な連続読み上げや処理のたびのフォーカス移動は避ける。
- 実際に観測できる件数・状態のみで進捗を表示し、根拠のない進捗率を出さない。

### アップロード一覧

- 元ファイル名を主表示として維持する。処理途中に「元名 → 長い保存名」を追加して行高を増やす方式は見直す。
- 保存用ファイル名は、最初から設けた補助欄または明示的に開く詳細で確認できるようにする。
- 長い名称は通常表示を一定行数に収めてもよいが、全文をクリック・タップ・キーボード操作で読めるようにする。hoverだけを唯一の導線にしない。
- 各ファイルの状態は同じ行内の状態欄で更新する。処理段階ごとに新しい行を追加しない。
- 標準の数件分を収める領域を確保し、多数時は一覧内スクロールを候補とする。狭い画面で過剰な二重スクロールや巨大な空白を作らない。
- 処理中表示を重ねる場合は、ファイル領域内の小さな進捗表示を第一案とする。一覧全体、ファイル別エラー、再試行導線、主要ボタンを覆い隠さない。
- 重ね表示がレイアウトを押さなくても、背後の操作が誤作動しないこと、クリック対象と見た目が一致することを確認する。

## 横断点検の対象

| 対象 | 点検・改善の中心 |
|---|---|
| 記録を追加の4タブ | 保存・添付・状態通知による移動。共通項目とタブ固有入力の保持は維持 |
| 過去の記録の編集・資料追加 | 保存・終了・再試行の位置、エラー表示、長い本文・資料名 |
| ナレッジ検索 | 条件・操作と回答領域の分離。応答時の不要なスクロールや操作位置変化 |
| 全文出力 | 件数・状態・プレビューの更新が対象確認、コピー、Docs、PDF操作を動かさないこと |
| 面談実績の集計・面談先サマリー | 条件・操作を維持し、結果領域内で状態更新。実行条件は変更しない |
| マスター・管理者ページ・ダイアログ | 状態通知・validationで入力や操作が不意に動かないこと |

全画面の一括作り直しは行わない。最初に登録・アップロードで最小の共通方式を作り、具体的に同じ問題がある箇所へ展開する。問題のない画面は変更しない。

## 実装時の検証方針

静止画の見栄えだけでなく、操作前後を比較する。

- ファイル未選択、1件、複数件、上限件数、長い元名・保存名、日本語名、処理中、成功、部分失敗、再試行を対象とする。
- 同じviewport・スクロール条件で、主要ボタンの位置・幅・高さを測る。通常通知だけによる移動は0を目標とし、測定上の許容差1 CSS pxは実装時の初期案とする。Work開始時に採用条件を固定する。
- 押した直後の短い状態と遅い応答の両方を観測する。総合的な性能指標だけで合格とせず、操作対象の移動を直接確認する。
- overlay、追従バー、長文エラーが操作・入力・フォーカスを隠さないことを確認する。
- desktopと狭い画面の変更箇所、拡大表示、キーボード操作を必要十分に検証する。無関係な画面・providerの再検証へ広げない。
- 保存先・保存内容、単一送信、retry identity、部分成功、競合拒否、クリア範囲等の既存契約を維持する。
- Validation Tierと実行環境での確認範囲は変更リスクに応じて実装Workで定める。本書だけを根拠に全画面再検証や追加deploymentを要求しない。

## 完了条件の考え方

主要な操作位置が状態変化で不意に動かず、処理結果と必要な対応が分かり、既存の保存・安全契約を維持したことを、対象操作のbefore/after証拠で確認できること。

本書は方針の記録であり、UI改善の実装完了・Work0070の追加検証完了を意味しない。
