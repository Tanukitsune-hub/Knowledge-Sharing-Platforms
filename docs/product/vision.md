# 部内共有ナレッジ基盤：プロダクト構想

作成日: 2026-08-02

ステータス: 構想・要件整理

## 1. エグゼクティブサマリー

本プロジェクトは、部内に散在する面談記録、面談資料、人物情報、ファンド情報、疑問点、フォローアップ事項を、利用者の追加負担を最小限に抑えながら共有資産へ変換するためのナレッジ基盤を構築するものです。

利用者は、普段どおりGoogle Docsで面談記録を作成し、Google Driveへ資料を保存します。システムはそれらを共有ドライブ上で整理し、面談先、人物、ファンド、テーマ、日付等で検索できるようにします。会社承認済みのAIを利用できる場合は、面談要約、主要論点、未確認事項、フォローアップ候補等を自動抽出します。

本基盤は、入力を管理するツールではなく、既に存在する記録を発見・再利用しやすくするツールとして設計します。

## 2. 解決する課題

現在の面談記録管理には、主に次の課題があります。

1. 蓄積された記録を横断的に活用できない
2. 過去の面談履歴を面談先・人物・ファンド別にすぐ確認できない
3. 固定的な入力項目が実際の面談内容に合わない
4. Excelのセル幅や入力方式により記録量・表現方法が制限される
5. 面談記録と関連資料が別々に保存され、相互参照しにくい
6. 記録を残す人だけが負担し、利用する人への便益が見えにくい
7. 個人Driveや個人アカウントに依存すると、異動・退職時に継続性が損なわれる

## 3. 目指す状態

利用者が次の操作を短時間で完了できる状態を目指します。

- 面談先を検索し、過去の面談履歴を確認する
- 人物名から、誰がいつ何回会ったかを確認する
- 過去の主要論点、未確認事項、フォローアップを確認する
- 面談記録から元のGoogle Docsを開く
- 関連する面談資料フォルダを開く
- 新しい面談記録を少ない入力で作成する
- 既存のGoogle DocsをURL登録だけで取り込む
- 面談前ブリーフを1操作で表示する

## 4. 想定利用者

初期対象は、同一部門内で面談、デューデリジェンス、モニタリング、関係管理を行う担当者です。

利用者を次の3区分で設計します。

| 区分 | 主な操作 |
|---|---|
| 一般利用者 | 検索、閲覧、面談登録、Docs作成、既存Docs登録 |
| ナレッジ管理者 | 表記揺れ修正、組織・人物統合、エラー確認、品質管理 |
| システム管理者 | App、Apps Script、権限、設定、AI接続、障害対応 |

## 5. 中核となる利用体験

### 5.1 探す

ホーム画面の中心に検索欄を置き、次の対象を横断検索します。

- 面談先・組織
- 人物
- ファンド・戦略
- 面談テーマ
- 面談記録本文
- 疑問点・未確認事項
- 資料名

検索結果は面談カードとして表示し、要約、主要テーマ、参加者、未確認事項数、元Docs、資料フォルダへのリンクを表示します。

### 5.2 登録する

登録方法は次の3つに限定します。

1. 新しい面談記録を作る
2. 既存のGoogle Docsを登録する
3. 過去データを取り込む

新規面談登録時の必須手入力は、原則として次の2項目だけとします。

- 面談日
- 面談先

面談タイトル、参加者、関連ファンド、テーマ等は、後から入力するかAI抽出候補を利用します。

### 5.3 面談を準備する

面談先を選択すると、次の情報を一覧表示します。

- 過去面談回数
- 最終面談日
- 過去に会った人物
- 直近面談の要約
- 継続している主要論点
- 未確認事項
- フォローアップ状況
- 関連する面談記録・資料

### 5.4 自分の状況を確認する

利用者ごとに、最近登録した面談、担当する確認事項、フォローアップ期限、処理エラー等を表示します。

AIが抽出した項目は自動的に正式TODOへせず、担当者と期限が確定したものだけを正式管理対象とします。

## 6. UI方針

一般利用者にはGoogle Sheetsを直接操作させません。

第一候補はAppSheetです。AppSheetが会社の契約・管理ポリシー上利用できない場合は、同じデータ構造と業務ロジックを利用するApps Script Web Appへ切り替えます。

利用者向けの主要メニューは次の4つまでに制限します。

1. 探す
2. 登録する
3. 面談準備
4. 自分の確認事項

画面上で専門的なデータベース用語、ファイルID、処理ステータス等を極力見せません。

## 7. Docsの設計思想

Docsの入力フォーマットを過度に固定しません。

新規作成用に簡易テンプレートを用意しますが、部内の既存様式や過去に他人が作成したDocsも受け入れます。横串を通す対象はDocsの書式ではなく、Docsから生成する共通ナレッジカードです。

標準テンプレートは次の最小構成とします。

```text
面談記録

面談メモ
自由に記載してください。

確認事項
任意。次回確認したい点があれば記載してください。

フォローアップ
任意。資料依頼や社内対応があれば記載してください。
```

面談日、面談先等はアプリ側に保持し、Docsへの二重入力を避けます。

## 8. 共通ナレッジカード

形式の異なるDocsから、次の共通項目を抽出・管理します。

| 項目 | 内容 |
|---|---|
| 面談要約 | 3〜5行の要約 |
| 主要論点 | 面談の重要テーマ |
| 事実 | 記録上確認された事実 |
| 発言・見解 | 面談相手または参加者の見解 |
| 所感・評価 | 記録者の評価・印象 |
| 未確認事項 | 次回確認すべき事項 |
| フォローアップ | 資料依頼、社内対応等 |
| 人物 | 参加者・登場人物 |
| 組織 | GP、投資先、アドバイザー等 |
| ファンド・戦略 | 関連ファンド・商品・戦略 |
| タグ | 検索用テーマ |
| 原資料 | Docs ID、URL、資料フォルダ |
| 処理情報 | 処理日時、モデル、処理状態 |

AIを利用できない場合でも、面談先、面談日、Docsリンク、資料リンクを中心とした索引として機能する設計とします。

## 9. 設計原則

1. 利用者の追加作業を最小化する
2. 入力項目より検索・再利用の便益を優先する
3. Docsの本文は自由記述を基本とする
4. AIによる分類は候補として扱い、正式記録を勝手に上書きしない
5. 人が修正した値はAI処理で上書きしない
6. AI出力から必ず元Docs・元資料へ戻れるようにする
7. 個人所有のファイル・アカウント・APIキーに依存しない
8. 段階導入とし、利用価値が確認されてから機能を増やす

## 10. 成功指標

初期目標は次のとおりです。

| 指標 | 目標 |
|---|---:|
| 既存Docsの登録時間 | 30秒以内 |
| 新規面談登録時間 | 1分以内 |
| 必須手入力項目 | 原則2項目 |
| 一般利用者によるSheets直接編集 | 0人 |
| 面談記録から原資料へ戻れる割合 | 100% |
| 主要GPの過去面談確認 | 3操作以内 |
| 面談前ブリーフ表示 | 1操作 |
| 個人アカウント依存資産 | 0件 |
| パイロット利用者の継続利用率 | 別途基準を設定 |

## 11. 初期対象外

- Gmail全体の自動解析
- 共有ドライブ全体を対象とする無制限なAI検索
- AIによる投資判断・正式記録の自動確定
- 高度なベクトル検索基盤の先行導入
- ファンドDD全工程の一括自動化
- 既存データの完全な初期正規化

## 12. プロダクトの最終像

利用者は、普段どおりDocsを書き、必要に応じて既存Docsを登録します。システムはDocsと資料を共有ドライブ上で整理し、面談履歴、人物、論点、疑問点、フォローアップを検索可能な形へ変換します。

次回面談時には、面談先を選択するだけで過去の経緯と確認事項を確認できます。入力を求める管理ツールではなく、使うほど準備時間が減る共有ナレッジ基盤を目指します。
