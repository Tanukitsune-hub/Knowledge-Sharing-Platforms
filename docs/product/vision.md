# Product Vision

## Purpose

面談記録とPitchbook等の投資関連資料を継続的に蓄積し、過去に得た情報を必要なときに簡単に取り出せる状態を作る。

対象はプライベートアセット業務を中心とするが、現段階では複雑な「ナレッジ共有プラットフォーム」を先に作ることを目的としない。

## Core user experience

利用者はGoogle Sheetsを直接編集せず、Google Apps Script HTML Serviceで作るシンプルなWeb Appから登録・管理を行う。Google SheetsはGPマスターと索引を保持するバックエンドとして使用する。

### 面談記録

面談登録画面では共通項目を少数に抑える。現時点の候補は以下。

- 日付
- GP
- 面談場所
- チーム
- アセットクラス
- その他、今後必要性が確認された最小限の項目

GPは共通GPマスターから選択する。選択肢にない場合は新規GPを登録できる。面談内容そのものは自由記載とする。

登録するとApps Scriptが一貫した形式のGoogle Docsを生成し、Shared Driveへ保存する。同時にGoogle Sheets側へ最低限の索引情報とドキュメントへのリンクを残す。

### Pitchbook等の資料

Pitchbook登録画面ではファイルのドラッグ＆ドロップと複数ファイルの一括登録を可能にする。

利用者が入力する共通項目は原則として以下の3項目だけとする。

- 日付
- GP
- アセットクラス

複数ファイルを同時に登録する場合はこの3項目を共通適用する。GPは面談登録と同じ共通GPマスターから選択し、選択肢にない場合は新規GPを登録できる。

保存ファイル名は利用者に自由入力させず、Apps Scriptが入力項目から一貫した名称を生成する。同一条件の複数ファイルは連番で識別し、元の拡張子を維持する。原資料はShared Driveへ保存し、Sheet側には最低限の索引とDrive参照を残す。

### GPマスター管理

GPマスター管理画面を用意する。

- 新規GP追加
- GP名称変更
- GP無効化
- GP再有効化

各GPには名称とは別に固定のGP IDを持たせる。名称変更後も過去の面談記録やPitchbookとの紐付けはGP IDで維持する。

無効化したGPは新規登録の選択肢から除外するが、過去データは残す。参照済みGPの物理削除はMVPでは行わない。重複GPの統合機能は必要性が確認された場合に追加検討する。

## Long-term outcome

将来的には、面談記録とPitchbook等を横断して、必要な情報を検索・参照・質問できる状態を目指す。

ただし、検索方式、AI Q&A、RAG、Vector DB、検索UI等は現時点では未決定であり、蓄積層を安定させた後に必要性を見て選択する。

## Principles

- シンプルさを最優先する。
- 利用者には必要な入力・管理画面だけを見せる。
- Google Sheetsの直接編集を通常運用にしない。
- 人間の入力負荷を増やしすぎない。
- 面談本文は自由記載のまま残す。
- 表記揺れが問題になる項目は共有マスターを使う。
- 原資料を正本として維持する。
- Google Workspaceを基本の保管・入力環境とする。
- 将来の検索技術を今の保存形式へ過度に埋め込まない。
- 実装していない機能を計画上の既定路線にしない。

## Explicit non-goals for now

- AppSheet前提のUI設計
- Apps Script HTML Service以外の外部Web基盤の先行開発
- Wiki、SNS、Like、コメント等の共有機能
- Gmail全体の取り込み
- 複雑なタグ体系
- 自動分類の作り込み
- Vector DBや高度なRAG基盤の先行導入
- AIによる投資判断や正式記録の自動確定

## Current phase

蓄積・登録UXのベースラインを順次確定している段階。Docsテンプレート、面談記録の命名規則、Pitchbook命名規則の細部、フォルダ構成、検索方式等は今後の検討で決める。
