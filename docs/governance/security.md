# 部内共有ナレッジ基盤：ガバナンスと情報管理

作成日: 2026-08-02

ステータス: 構想・要件整理

## 1. 基本方針

本基盤は、面談記録、未公開情報、個人情報、投資判断に関わる情報を扱う可能性があります。技術的に実現可能であることと、社内規程上利用可能であることを分けて確認します。

次の原則を採用します。

1. 原資料はGoogle Workspaceの共有ドライブで管理する
2. 個人アカウントや個人Driveを本番正本にしない
3. 権限はGoogleグループ単位で付与する
4. 最小権限を基本とする
5. AI処理対象を明示的に制御する
6. AI出力から原資料へ追跡できるようにする
7. 実際の面談記録、個人情報、認証情報をGitHubへ保存しない
8. 管理者交代・アカウント無効化後も継続できる設計とする

## 2. データの所在

| データ | 正本 | 備考 |
|---|---|---|
| 面談記録 | 共有ドライブ内Google Docs | 自由記述の原資料 |
| 面談資料 | 共有ドライブ内Google Drive | 面談別または組織別に整理 |
| 面談索引 | システム用共有ドライブ内Google Sheets | 一般利用者は直接編集しない |
| AI抽出結果 | Google Sheetsまたは承認済みデータストア | 原資料IDを必須とする |
| 実行ログ | システム用共有ドライブ | 保存期間を別途定義 |
| ソースコード | GitHub | 機密データ・秘密値を含めない |
| APIキー・秘密値 | 会社承認済みのSecret管理方式 | コード・Sheets・GitHubへ直書きしない |

## 3. 共有ドライブと所有権

本番資産は、原則として次の2つの共有ドライブへ配置します。

- 部内ナレッジ・コンテンツ
- 部内ナレッジ・システム

個人のマイドライブ上にある既存Docsは、正式登録時に次のいずれかを行います。

1. 共有ドライブへ移動する
2. 共有ドライブへ保管版をコピーする
3. 外部参照として登録し、継続性リスクを表示する

外部参照の場合は、元URL、所有区分、最終アクセス確認日時を記録します。

## 4. 権限モデル

### 4.1 役割

| 役割 | 権限概要 |
|---|---|
| 一般利用者 | 記録・資料の閲覧、面談登録、許可範囲内の編集 |
| ナレッジ管理者 | 組織・人物・タグの正規化、重複統合、品質管理 |
| システム管理者 | App、Apps Script、設定、権限、ログ、障害対応 |
| 監査・閲覧者 | 許可された範囲の読み取りのみ |

### 4.2 権限付与

- 個人への直接付与を最小限にする
- Googleグループを利用する
- 異動・退職時はグループから削除する
- システム用共有ドライブは一般利用者へ共有しない
- App UIで必要なデータだけを公開する
- 管理用列、設定、ログを一般利用者から隠す

### 4.3 App実行方式

AppSheetまたはWeb Appが作成者権限で動作する場合、UIで公開したデータ範囲が実質的なアクセス範囲になります。したがって、バックエンドの機密設定と一般利用データを同じテーブル・同じビューに混在させません。

## 5. アカウントと運用主体

共有ドライブにファイルを置くだけでは、Apps Scriptのトリガー、Web Appデプロイ、AppSheet所有者等の個人依存は解消されません。

推奨方針:

- 部門管理用Workspaceアカウントを運用主体とする
- AppSheetアプリ所有者を部門管理用アカウントとする
- Apps Scriptの本番デプロイを部門管理用アカウントで行う
- 定期トリガーを部門管理用アカウントで作成する
- システム管理権限を2名以上へ付与する
- 管理アカウントの認証・回復手順を組織管理する

部門管理用アカウントを作成できない場合は、所有者交代手順、トリガー再作成手順、デプロイ再設定手順を明文化し、定期的に引継ぎテストを行います。

## 6. AI利用方針

### 6.1 利用条件

AI処理は、会社が承認したGemini API、Vertex AIまたは同等の管理環境に限定します。

次の条件が確定するまで、実データをAIへ送信しません。

- 利用規約
- データが製品改善に利用されるか
- ログ保持期間
- 利用リージョン
- データ処理者・再委託先
- 機密情報・個人情報の取扱い
- 社内情報管理部門の承認
- 認証・秘密値管理方法

無料枠、個人契約、個人AI Studio等を本番利用しません。

### 6.2 AI処理対象

各面談・ファイルに次の情報を持たせます。

- information_classification
- ai_process_allowed
- ai_processing_scope
- human_review_required

AI処理対象は、`ai_process_allowed = TRUE`の記録に限定します。

### 6.3 AIの役割

AIは次の補助処理に利用します。

- 要約
- 主要論点抽出
- 人物・組織・ファンド候補抽出
- 未確認事項候補
- フォローアップ候補
- タグ候補
- 関連記録を絞った上での質問回答

AIに次の権限を与えません。

- 正式な投資判断の確定
- 原資料の削除
- 人が確定した情報の無断上書き
- 共有ドライブ全体への無制限アクセス
- 外部への自動送信

### 6.4 出典と追跡可能性

AI出力には次を記録します。

- source_file_id
- source_url
- source_excerptまたは位置情報
- model_name
- prompt_version
- output_schema_version
- processed_at
- human_confirmed

AI回答画面には、元Docsと面談日を表示します。

## 7. 人による確認

すべてのAI出力を重いレビュー工程へ送るのではなく、次の項目を確認対象とします。

- 面談先
- 面談日
- 参加者
- 関連ファンド
- 重要な事実
- 未確認事項
- 正式TODO候補
- 低確信項目

人が修正・確定した項目には、`human_confirmed = TRUE`を設定し、将来のAI再処理で上書きしません。

## 8. ログと監査

最低限、次の操作を記録します。

- 面談登録
- Docs作成
- ファイル移動・コピー
- 権限確認
- AI処理
- AI処理失敗
- 人による修正・確定
- ファイル削除・リンク切れ
- 管理設定変更

ログ項目:

- event_id
- event_type
- user_id
- meeting_id
- file_id
- timestamp
- result
- error_code
- correlation_id

ログ保存期間は社内規程と運用上の必要性を踏まえて決定します。

## 9. データ品質

### 9.1 表記揺れ

組織名、人物名、ファンド名は、正規名称と別名を分けて管理します。

AIが新しい名称を検出した場合、自動的に新規マスターを確定せず、既存候補との一致を確認します。

### 9.2 重複

重複統合時も、元のmeeting_id、file_id、変更履歴を保持します。

### 9.3 事実と所感

AI抽出では、少なくとも次を分離します。

- 記録上の事実
- 面談相手の発言・見解
- 記録者の所感・評価
- システムまたはAIによる推論

推論は事実として表示しません。

## 10. 保存・削除

次のルールをPhase 0で確定します。

- 面談記録の保存期間
- 退職者・異動者の作成記録の扱い
- 削除権限
- 誤登録時の復旧期間
- AI派生データの削除方法
- 原資料削除時の索引・キャッシュ削除方法
- バックアップ保存期間

原資料を削除した場合、関連するAI要約、抽出項目、検索インデックスも追跡して削除できる設計とします。

## 11. バックアップと復旧

- Backend Spreadsheetを定期バックアップする
- Apps ScriptコードをGitHubで管理する
- App設定のエクスポートまたは再構築手順を保持する
- プロンプトと出力スキーマをバージョン管理する
- 共有ドライブ構成を文書化する
- 復旧手順を定期的にテストする

目標復旧対象:

- 面談索引
- Docs・資料リンク
- 組織・人物マスター
- AI処理履歴
- App UI
- Apps Scriptデプロイ
- 定期トリガー

## 12. GitHub運用

このリポジトリが公開設定である場合を含め、次の情報を保存しません。

- 実際の面談記録
- 面談相手の個人情報
- 未公開ファンド情報
- 社内組織名・利用者一覧
- 実際の共有ドライブID
- Spreadsheet ID
- Docs ID
- APIキー
- OAuth認証情報
- アクセストークン
- 本番ログ

GitHubへ保存するもの:

- 設計書
- ソースコード
- 匿名化したサンプル
- テスト
- デプロイ手順
- 変更履歴

`.gitignore`、Secret scanning、コードレビューを利用し、秘密値がcommitされた場合の失効・再発行手順を用意します。

## 13. インシデント対応

想定インシデント:

- 誤った外部共有
- 権限過大付与
- APIキー漏えい
- 不正なAI処理
- 機密情報の誤送信
- ファイル大量削除
- 利用者アカウント侵害
- 誤ったAI要約の業務利用

初動手順:

1. 対象機能またはAI処理を停止する
2. 影響範囲を特定する
3. 権限・キーを失効または変更する
4. ログと原資料を保全する
5. 社内の所定窓口へ報告する
6. 復旧・再発防止策を記録する

## 14. 本番開始条件

- 共有ドライブと権限設計が承認されている
- 運用主体と代替管理者が定まっている
- 情報区分とAI処理可否が明確である
- 秘密値管理方式が承認されている
- 原資料への追跡可能性が確認されている
- 削除・バックアップ・復旧手順が存在する
- 一般利用者が管理データへ直接アクセスできない
- 匿名化データによる権限・障害テストが完了している
